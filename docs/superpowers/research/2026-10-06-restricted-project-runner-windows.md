### Bootstrap authority: facts versus inference

**Documented:** -NoProfile skips PowerShell profiles; it does not authenticate -Command/-EncodedCommand/stdin. Execution policy is not a security boundary. CLR profiling can be selected during CLR initialization from environment variables, before the first script command. Same-desktop UAC elevation is not a security boundary. These facts do not authorize disabling UAC or changing policies. [Host parameters](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_powershell_exe?view=powershell-5.1), [execution policy](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_execution_policies?view=powershell-5.1), [CLR startup](https://learn.microsoft.com/en-us/dotnet/framework/unmanaged-api/profiling/setting-up-a-profiling-environment), [Microsoft UAC boundary explanation](https://learn.microsoft.com/en-us/troubleshoot/windows-server/windows-security/disable-user-account-control).

**Inference for R3:** the valid Microsoft catalog signature/hash authenticates the host, not the owner-approved command bytes or payload-hash literals. A digest of a non-executable draft is not an authenticated executable procedure. A same-user launcher can substitute commands, expected hashes or startup environment while invoking the genuine host. Post-copy hashing protects only after a trustworthy expected value/implementation is established. The plan's prior independently trusted input prerequisite is real and unresolved, not a standard Windows API supplied by clicking UAC.

A concrete conditional route needs an independently provisioned protected verifier/launcher and pinned release-envelope verification key, with owner-approved procedure/resource/hashes authenticated before interpretation. R3 establishes neither. Printed/out-of-band reference plus local typing does not prove protected receiver/startup. A signature key generated/held by the hostile ordinary user, clipboard, mutable repo envelope or broad publisher label is insufficient. No complete protected PowerShell startup mechanism is selected or proved; the missing initial provisioning/approval channel is the exact platform/product decision.

### SCM: documented guarantees

SCM creates the initial service security descriptor. Documented ordinary-user default rights omit start/configuration/delete/DAC/owner writes and include USER_DEFINED_CONTROL and read/interrogate rights. **The documentation does not specify the service object's initial owner SID.** [Service security](https://learn.microsoft.com/en-us/windows/win32/services/service-security-and-access-rights).

CreateServiceW accepts a fixed startup type including DISABLED, image and service account, but no SECURITY_ATTRIBUTES/custom initial descriptor. General new-object ownership follows the creator's primary/impersonation token; it does not specify the SCM client/server context used here. A caller TokenOwner test is not an SCM-owner guarantee. [CreateServiceW](https://learn.microsoft.com/en-us/windows/win32/api/winsvc/nf-winsvc-createservicew), [general ownership](https://learn.microsoft.com/en-us/windows/win32/secauthz/owner-of-a-new-object).

Controls are not sent to a stopped service; starting a disabled service fails. This permits a bounded **inert default-DACL phase**, followed by final hardening before enabling/start, provided initial owner is independently safe. LockServiceDatabase has no locking effect on Vista and later. [ControlService](https://learn.microsoft.com/en-us/windows/win32/api/winsvc/nf-winsvc-controlservice), [StartService](https://learn.microsoft.com/en-us/windows/win32/api/winsvc/nf-winsvc-startservicew), [database lock](https://learn.microsoft.com/en-us/windows/win32/api/winsvc/nf-winsvc-lockservicedatabase).

MsiLockPermissionsEx supplies security during InstallServices; its description does not establish an atomic CreateService-with-custom-SD primitive. Deferred no-impersonate MSI custom actions can run in system context, which may simplify creator identity **if the signed package/channel is already trusted**, but expands the current package scope and still needs native evidence. [Service permissions table](https://learn.microsoft.com/en-us/windows/win32/msi/msilockpermissionsex-table), [custom-action execution options](https://learn.microsoft.com/en-us/windows/win32/msi/custom-action-in-script-execution-options).

### R3 static finding / required native evidence

R3 InitialServiceSecuritySafe rejects ordinary USER_DEFINED_CONTROL, so it is expected to reject Microsoft's ordinary default grants; DefaultTokenOwnerIsAdministrators proves only caller TokenOwner. Do not remove the check indiscriminately or claim compilation proves a safe initial owner. The plan defines disabled/stopped-only control acceptance, final DACL before configuration/enablement, partial-state journal/remover changes and focused static negative tests.

Separately authorized Gate B must observe actual initial owner/DACL/state, same-user effective rights/control non-delivery at a pre-hardening barrier, final configuration, native token, protected copy/loader/handle locking and crash recovery. Sampling the first readback cannot retroactively exclude an earlier unsafe owner window; a supported creation-context argument remains necessary. No OS-native test has run in this research task.

### Recovery guarantees and limits

Creation-time SECURITY_ATTRIBUTES and explicit non-inherited ownership/DACL are available for files. Sharing modes can deny write/delete while verification/execution uses a held file handle. FlushFileBuffers flushes buffered file information; it does not make creation plus an independently written ownership record one atomic transaction. [CreateFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew), [FlushFileBuffers](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-flushfilebuffers).

Design inference: an independent bounded protected staging ledger outside staging/install permits cleanup-last and records exact identities; initial-ledger/root/create-before-commit crash gaps must remain BLOCKED for a newly reviewed exact recovery manifest. Owner/DACL/path/hash alone cannot adopt unknown leftovers. The plan specifies all resources, 64 KiB limit, record/flush sequence, staged-remover retention and final ledger deletion. Native durability, loader/unload and partial cleanup remain Gate B obligations, not static PASS.

### Trusted confirmation follow-up — secure CredUI candidate

**TRUSTED CONFIRMATION DESIGN: APPROVED**, meaning sufficiently precise for a bounded fail-closed feasibility investigation. **Authentication versus contextual Approval:** UserConsentVerifier returns a verification enum; owner main cannot carry that enum across a trust boundary as proof. [Desktop interop](https://learn.microsoft.com/en-us/windows/win32/api/userconsentverifierinterop/nf-userconsentverifierinterop-iuserconsentverifierinterop-requestverificationforwindowasync), [WebAuthn availability](https://learn.microsoft.com/en-us/windows/win32/webauthn/-webauthn-portal).

Inference: these are useful key/UI primitives, not a guarantee of fresh per-transaction protected display from a service. No selected KSP-specific mechanism satisfies the exact record/host/decision path. [UI policy](https://learn.microsoft.com/en-us/windows/win32/api/ncrypt/ns-ncrypt-ncrypt_ui_policy), [KSP properties](https://learn.microsoft.com/en-us/windows/win32/seccng/key-storage-property-identifiers).

Inference: a fixed custom provider that verifies actual SYSTEM/secure-desktop/session context, independently fetches service truth and directly sends an explicit decision offers a coherent protected-presenter architecture. This does **not** establish the actual host token or desktop-object visibility for every invocation; incompatible hosting must reject, not get a privilege workaround. [Secure CredUI](https://learn.microsoft.com/en-us/windows/win32/api/wincred/nf-wincred-creduipromptforwindowscredentialsw), [custom providers](https://learn.microsoft.com/en-us/windows/win32/secauthn/credential-providers-in-windows), [Windows 10 secure desktop](https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-10/security/threat-protection/security-policy-settings/user-account-control-switch-to-the-secure-desktop-when-prompting-for-elevation).

Automatic default selection may immediately invoke GetSerialization. Inference: both automatic flags must be false; a callback alone cannot be interpreted as human approval. Trusted explicit submit is required, with nonce/revision/digest bound to the same direct SYSTEM-authenticated pipe. Owner-launcher result is never authority. [GetCredentialCount](https://learn.microsoft.com/en-us/windows/win32/api/credentialprovider/nf-credentialprovider-icredentialprovider-getcredentialcount), [SetSelected](https://learn.microsoft.com/en-us/windows/win32/api/credentialprovider/nf-credentialprovider-icredentialprovidercredential-setselected).

### Control identity is separable; human decision is a different inlet

Virtual service accounts/service SIDs support ACL-separated code/state/IPC without application-held account passwords. Inference: a low-privilege control service can own Runner Kernel/Policy/Approval/admission and be the exclusive ordinary caller of the fixed helper. This meets existing-account startup UX more simply than a managed second human account. It does not authenticate a same-user Desktop's claimed human approval. Domain machine-credential behavior is not an offline guarantee. [CreateService](https://learn.microsoft.com/en-us/windows/win32/api/winsvc/nf-winsvc-createservicea), [service SID](https://learn.microsoft.com/en-us/windows/win32/api/winsvc/ns-winsvc-service_sid_info).

Local pipe DACL/logon identity, first-instance creation and remote rejection are supported. Individual data rights avoid granting server-instance creation through generic write. Identification-level inspection can authenticate an allowed principal without arbitrary client impersonation; it cannot prove an application-specific human decision for every program sharing that principal. Inference: owner endpoint carries intent/status only; service endpoint carries authority; both need authenticated server identity and bounded protocol. [Pipe security](https://learn.microsoft.com/en-us/windows/win32/ipc/named-pipe-security-and-access-rights), [CreateNamedPipe](https://learn.microsoft.com/en-us/windows/win32/api/namedpipeapi/nf-namedpipeapi-createnamedpipew), [ImpersonateNamedPipeClient](https://learn.microsoft.com/en-us/windows/win32/api/namedpipeapi/nf-namedpipeapi-impersonatenamedpipeclient).

User-scoped DPAPI generally decrypts under that user's logon credentials; process security is principal/access-right based. A same-user file secret or genuine copied binary therefore does not provide the required distinct authority. Inference: service-only non-exportable signing can protect origin, but a same-user-callable approve/sign-anything endpoint still fails. A private signature is optional for the minimum authenticated local service hop, not a replacement for Policy/Approval. [DPAPI](https://learn.microsoft.com/en-us/windows/win32/api/dpapi/nf-dpapi-cryptprotectdata), [process security](https://learn.microsoft.com/en-us/windows/win32/procthread/process-security-and-access-rights), [CNG properties](https://learn.microsoft.com/en-us/windows/win32/seccng/key-storage-property-identifiers), [NCryptSignHash](https://learn.microsoft.com/en-us/windows/win32/api/ncrypt/nf-ncrypt-ncryptsignhash).

Custom AppContainer process creation supplies SECURITY_CAPABILITIES including AppContainerSid, and a profile SID can be derived from its name. Inference: a custom profile SID alone is not exclusive trusted-program provenance. This does not establish that every genuine MSIX package identity is forgeable; package activation/integrity and protected UI would need a different full proof. No such complete package-based approval architecture was established here. Microsoft describes user/session boundaries and Fast User Switching that keeps the original account's applications running. Inference: a genuine non-admin owner separated from a trusted reviewer account/session can support approval isolation; reviewer code/credentials/session join TCB. It is not a sandbox against reviewer compromise or full administrator control. Manual switching is disqualified by the latest UX requirement. An automatic route must still deliver actual isolated input and exact immutable service review, not mirror attacker-controlled owner UI. Inference: neither documented call supplies creation of a distinct Winlogon interactive GUI session. ### Supported identity versus actual authority

Windows supports virtual service accounts named `NT SERVICE\ServiceName`, without a supplied password; service SIDs support resource ACL isolation. Domain network access can use machine credentials. Inference: separate service identities reduce credential/resource coupling but do not make a helper offline or constrain Hyper-V objects. [CreateService](https://learn.microsoft.com/en-us/windows/win32/api/winsvc/nf-winsvc-createservicea), [service SID](https://learn.microsoft.com/en-us/windows/win32/api/winsvc/ns-winsvc-service_sid_info), [service accounts](https://learn.microsoft.com/en-us/windows-server/identity/ad-ds/manage/understand-service-accounts).

Hyper-V Administrators has unrestricted Hyper-V feature access. Microsoft explicitly excludes this group as a security boundary from full Administrators. Inference: a helper/watchdog with that membership is administrative TCB code; fixed verbs and one-slot checks restrict its exposed protocol, not a compromised service's underlying authority. A virtual account does not turn this into per-VM least privilege. Exact target-build account/provider access still needs a spike. No supported complete per-VM create/reset/lifecycle delegation was established here. [Hyper-V Administrators](https://learn.microsoft.com/en-us/windows-server/identity/ad-ds/manage/understand-security-groups#hyper-v-administrators), [MSRC security criteria](https://www.microsoft.com/en-us/msrc/windows-security-servicing-criteria).

SCM supports declaring required privileges and stripping others at service startup; shared-process services receive the union, and SeChangeNotifyPrivilege is retained. Service-control rights are distinct from pipe access. Inference: use own-process services, explicit minimal privilege policy and status-only ordinary-user control, then inspect real tokens. Do not invent SeDebug/backup/restore/TCB privileges to overcome a failed probe. [Required privileges](https://learn.microsoft.com/en-us/windows/win32/api/winsvc/ns-winsvc-service_required_privileges_infow), [service security](https://learn.microsoft.com/en-us/windows/win32/services/service-security-and-access-rights).

### Pipe authentication does not identify SUD-D application approval

Explicit pipe DACLs/logon SIDs and individual access rights are available; generic-write includes server-instance creation rights. CreateNamedPipe supports remote rejection, first-instance ownership and overlapped IO. Its buffer sizes are advisory. Inference: bound protocol allocation/instances independently and verify server identity; neither a pipe name nor buffer setting is an authentication/capacity guarantee. [Pipe security](https://learn.microsoft.com/en-us/windows/win32/ipc/named-pipe-security-and-access-rights), [CreateNamedPipe](https://learn.microsoft.com/en-us/windows/win32/api/namedpipeapi/nf-namedpipeapi-createnamedpipew).

ImpersonateNamedPipeClient identifies the security context of the last read message. Identification-level access is supported without requiring SeImpersonatePrivilege under the documented conditions. Failure must be checked; otherwise work may run as the privileged server. Inference: inspect/revert for authorization only, never dispatch Hyper-V under an unchecked client token. [ImpersonateNamedPipeClient](https://learn.microsoft.com/en-us/windows/win32/api/namedpipeapi/nf-namedpipeapi-impersonatenamedpipeclient).

SSPI authenticates a principal and supports message protection; requested mutual/sequence attributes must actually be negotiated and checked. It does not create a distinct application identity for two callers with the same Windows principal. [InitializeSecurityContext](https://learn.microsoft.com/en-us/windows/win32/api/sspi/nf-sspi-initializesecuritycontextw), [EncryptMessage](https://learn.microsoft.com/en-us/windows/win32/api/sspi/nf-sspi-encryptmessage).

Pipe client PID and image-path APIs return process metadata; WinVerifyTrust evaluates a specified object/file. Process access rights separately govern memory, thread and handle access. User-bound DPAPI ordinarily permits decryption with the same logon credentials; machine-bound protection is broader. Inference: those checks alone do not prove that an ordinary same-user Electron/Node request came from protected SUD-D code or passed Approval; also consider second genuine process, mutable JS and injection/handle theft. This is a gap in this candidate, not a claim that all Windows application isolation is impossible. [Client PID](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-getnamedpipeclientprocessid), [image path](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-queryfullprocessimagenamew), [WinVerifyTrust](https://learn.microsoft.com/en-us/windows/win32/api/wintrust/nf-wintrust-winverifytrust), [process access](https://learn.microsoft.com/en-us/windows/win32/procthread/process-security-and-access-rights), [DPAPI](https://learn.microsoft.com/en-us/windows/win32/api/dpapi/nf-dpapi-cryptprotectdata).

Local facts at `7e4c546`: `packages/desktop/package.json` specifies per-user NSIS install, elevation disabled and signAndEditExecutable=false. `packages/application/src/approval-service.ts` owns keyed approval coordination in the application runtime. `project-runner-service.ts` exposes start(snapshot), with host paths in the snapshot, not an isolated helper grant contract. Gateway is a separate Node process; production gateway composition does not expose runner.start. Inference: neither an application-specific protected authorization anchor nor a helper-verifiable grant issuer has been established by existing foundations. A cryptographic signature from a same-user-callable sign-anything service would leave the gap open.

### Recovery and termination are separate

SCM failure actions schedule recovery after eligible service failure/status; no documented live-helper lease or hang deadline is supplied. Inference: restart is operational recovery, not independent VM termination. [Failure actions](https://learn.microsoft.com/en-us/windows/win32/api/winsvc/ns-winsvc-service_failure_actionsw), [failure flags](https://learn.microsoft.com/en-us/windows/win32/api/winsvc/ns-winsvc-service_failure_actions_flag).

Stop-VM TurnOff removes virtual power; Force includes a guest shutdown wait and is not the required immediate power-off equivalent. WMI RequestStateChange can return an asynchronous job and its TimeoutPeriod is unused. Inference: an independent watchdog must observe Off, not only submit a stop. Reviewed documentation supplies no universal wall-clock bound if VMMS/host infrastructure fails; two cooperating user-mode services also cannot prove termination after both die. A failed deadline keeps admission blocked and cannot be relabeled safe stopped state. [Stop-VM](https://learn.microsoft.com/en-us/powershell/module/hyper-v/stop-vm?view=windowsserver2025-ps), [RequestStateChange](https://learn.microsoft.com/en-us/windows/win32/hyperv_v2/requeststatechange-msvm-computersystem).

Research conclusion: Windows Service is the best conditional lifecycle container; application-specific authorization and independent finite termination remain prerequisites. Platform API existence is not target-host feasibility PASS. No Home virtualization/RAM assessment, implementation, production authority or global OS support-policy change follows from this research.

### Primary-source findings and implications

**Disk versus persistence authority.** Fixed VHD preallocates requested backing space; dynamic creation does not reserve its maximum against host free space; differencing creates additional writable state. VHDX has its own format metadata/logs, so virtual capacity is not identical to backing-file bytes. Attach privilege and disk geometry must be read back. Our inference: use fixed allocation with explicitly budgeted backing metadata, no expansion/differencing, and a separate execution boundary that cannot acquire another disk. [About VHD](https://learn.microsoft.com/en-us/windows/win32/vstor/about-vhd), [VHDX specification](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-vhdx/83f6b700-6216-40f0-aa99-9fcb421206e2), [AttachVirtualDisk](https://learn.microsoft.com/en-us/windows/win32/api/virtdisk/nf-virtdisk-attachvirtualdisk).

**Quota details.** NTFS charges file-owner SID and all data-stream lengths, excludes associated metadata, and compression does not change charged length. Hard denial must be enabled, not confused with warning/logging. Sparse logical length is not physical allocation. New-object ownership depends on token/creation context; a capability SID is not automatic file ownership. Setting an AppContainer-SID quota entry is not established as a supported per-job mechanism by the reviewed sources; even a successfully created entry would not charge files owned by a different SID. Hence neither quota nor AppContainer identity is a per-job physical disk limit; ownership/hive-service writes and every volume would require proof. Concurrent denial is a native enforcement mechanism only within these semantics. [Disk quota limits](https://learn.microsoft.com/en-us/windows/win32/fileio/disk-quota-limits), [fsutil quota](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/fsutil-quota), [Sparse files](https://learn.microsoft.com/en-us/windows/win32/fileio/sparse-files), [Owner of a new object](https://learn.microsoft.com/en-us/windows/win32/secauthz/owner-of-a-new-object).

**Registry containment.** Windows persists hives and associated supporting files, including system hives under SystemRoot and user hive files. Selecting a complete Windows guest disk puts those guest files, not just runner-created output, within finite guest sectors. It does not constrain host Hyper-V registration/other host hives. No host registry projection is allowed. [Registry hives](https://learn.microsoft.com/en-us/windows/win32/sysinfo/registry-hives).

**Sandbox.** It is disposable hypervisor isolation; supported editions exclude Home. The documented .wsb fields include MemoryInMB but not writable-disk capacity. Networking and clipboard defaults and writable mapped folders are unsuitable defaults for P0. Turning these off removes channels but is not itself a total storage proof. [Sandbox overview](https://learn.microsoft.com/en-us/windows/security/application-security/application-isolation/windows-sandbox/), [WSB configuration](https://learn.microsoft.com/en-us/windows/security/application-security/application-isolation/windows-sandbox/windows-sandbox-configure-using-wsb-file).

**Containers/HCS.** Microsoft distinguishes shared-kernel process isolation from Hyper-V isolation; host mounts, ports, devices and named pipes pierce separation. Its security guidance does not treat process isolation as a robust hostile boundary. Scratch/layers reside on host; the reviewed container storage size documentation describes visible capacity, not all retained host allocation. HCS StorageQoS is IOPS/bandwidth, not a byte ceiling; versioned schema support must be checked against build 19045, not inferred from latest docs. [Isolation modes](https://learn.microsoft.com/en-us/virtualization/windowscontainers/manage-containers/hyperv-container), [Container security](https://learn.microsoft.com/en-us/virtualization/windowscontainers/manage-containers/container-security), [Requirements](https://learn.microsoft.com/en-us/virtualization/windowscontainers/deploy-containers/system-requirements), [Container storage](https://learn.microsoft.com/en-us/virtualization/windowscontainers/manage-containers/container-storage), [HCS schema](https://learn.microsoft.com/en-us/virtualization/api/hcs/schemareference), [Virtualization APIs / WHP](https://learn.microsoft.com/en-us/virtualization/api/).

**Full VM prerequisites and privileges.** Hyper-V client support includes Win10/11 Pro/Enterprise, requires SLAT, virtualization enabled in firmware and sufficient host/guest RAM. Enabling is privileged and can require reboot. Management rights are broad: putting Desktop in Hyper-V Administrators is not a narrowly scoped unprivileged runtime. Proposed fixed helper retains privileged management authority during jobs; one-time installation does not erase that fact. Avoid WinRM/remoting configuration. [Hardware/edition requirements](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/host-hardware-requirements), [Install Hyper-V](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/get-started/install-hyper-v), [Host management permissions](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/manage/remotely-manage-hyper-v-hosts).

**Bounded non-IP return.** Hyper-V sockets support Windows10+ host/guest, a user-mode stream over VMBus, using AF_HYPERV/SOCK_STREAM/HV_PROTOCOL_RAW and VM/service GUIDs. Host service registration is administrative. Wildcard VM IDs admit other partitions; our design uses the exact owned VM endpoint, fenced attempt and bounded untrusted frames instead. This is transport, not filesystem/network authority or trustworthy guest result evidence. Large media throughput needs later measurement. [Hyper-V sockets](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/make-integration-service).

**Auxiliary state matters.** Checkpoints create additional AVHDX; integration services open extra channels. Our proposal disables checkpoints, save-state/automatic restart and unnecessary integrations rather than counting cleanup as a cap. Hypervisor/VM configuration, paging, event/WER state and SUD-D audit/database growth still require a complete bounded host inventory. No primary source reviewed guarantees that a guest VHD alone bounds these. [Checkpoints](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/checkpoints), [Integration services](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/manage/Manage-Hyper-V-integration-services).

**Servicing/product constraint.** Win10 ordinary support ended 2025-10-14; the observed build does not prove current ESU/security coverage. Spike must record actual host/guest servicing and guest license/image provenance. Prefer a maintained supported deployment, but this task does not silently raise SUD-D's global Windows minimum or claim Home support. [Windows release information](https://learn.microsoft.com/en-us/windows/release-health/release-information), [Supported Windows guests](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/supported-windows-guest-operating-systems-for-hyper-v-on-windows).

## Findings

1. **Job Objects govern lifecycle and resource accounting.** They group assigned processes and apply limits; closing the **last** Job Object handle kills associated processes when `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` is set. Disable both `JOB_OBJECT_LIMIT_BREAKAWAY_OK` and `JOB_OBJECT_LIMIT_SILENT_BREAKAWAY_OK`. Normal `CreateProcess` children inherit membership, but Microsoft explicitly identifies `Win32_Process.Create` children as an exception. Therefore a Job Object alone cannot establish that every externally broker-created descendant is owned or terminated. Nested jobs are supported from Windows 8 onward; host job compatibility still needs a real launch test. [Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects).

2. **Assign before executing project code.** `CREATE_SUSPENDED` prevents the primary thread running until `ResumeThread`; `AssignProcessToJobObject` applies limits after association and can fail. Recommended sequence: configure job and isolation, create suspended process, assign and verify membership, then resume. On any setup/assignment/resume failure, terminate the suspended child and return failure; never resume as a fallback. Keep the job handle private and non-inheritable so an extra handle cannot defer last-handle cleanup. This sequence is a design inference from the API semantics. [Process Creation Flags](https://learn.microsoft.com/en-us/windows/win32/procthread/process-creation-flags), [AssignProcessToJobObject](https://learn.microsoft.com/en-us/windows/win32/api/jobapi2/nf-jobapi2-assignprocesstojobobject).

3. **`cwd` and sanitized environment are launch hygiene, not containment.** `CreateProcessW` normally uses the caller's security context; environment and initial directory are parameters independent of that context. Inherited handles retain their original rights. Consequently a workspace `cwd`, an executable allowlist and clean environment do not revoke filesystem/network/process authority. Use a fully qualified application path, explicit environment and narrowly controlled handle inheritance, in addition to OS isolation. [CreateProcessW](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessw).

4. **AppContainer supplies a real resource-access boundary.** Its package/capability SIDs and user/group rights both participate in DACL checks; effective access is their intersection. Without network capability, network access is denied. Regular AppContainers still have default access to some system resources; LPAC requires additional explicit capabilities for resources regular AppContainers can access. Launch uses `STARTUPINFOEX` security-capability attributes; setting ordinary process launch options does not create this boundary. Compatibility of Node/Python/build tools with the chosen AppContainer/LPAC profile remains unproven and must be tested. [Launch an AppContainer](https://learn.microsoft.com/en-us/windows/win32/secauthz/implementing-an-appcontainer).

5. **Network capability is not an endpoint allowlist.** Microsoft's networking capability model separates Internet client/server and private-network access. A permitted Internet capability is broader than one approved provider destination. Endpoint restrictions require another enforced boundary, such as a reviewed broker or firewall policy; do not rely on a declared destination field or runner cooperation. Treat this as an architectural inference. [Network isolation](https://learn.microsoft.com/en-us/windows/win32/secauthz/appcontainer-isolation), [Windows Firewall capability filtering](https://learn.microsoft.com/en-us/windows/security/operating-system-security/network-security/windows-firewall/troubleshooting-uwp-firewall).

6. **Denying deletion does not deny destruction.** Windows distinguishes `FILE_WRITE_DATA`, append, `DELETE` and directory delete-child rights. Delete/rename can be authorized through either file delete or parent delete-child permission; new-file creation has further handle-rights caveats. `SetEndOfFile` truncates with a writable handle. Thus an ordinary writable source grant can destroy content without calling Delete, and recovery cannot be guaranteed by an API-level delete gate. [File access rights](https://learn.microsoft.com/en-us/windows/win32/fileio/file-access-rights-constants), [DeleteFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-deletefilew), [SetEndOfFile](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-setendoffile).

## Fail-closed recommendation

Keep runner execution unavailable until a disposable native launch proof establishes the chosen OS isolation profile and negative paths. First candidate: no direct network or secrets; read-only approved inputs; writable disposable staging/output; no write grant on original Workspace or internal roots. Use Job Objects for cleanup **alongside** AppContainer/LPAC or another proven isolation boundary. Import reviewed artifacts through existing Policy/Approval/Audit/Recovery boundaries, preserving originals. Staging alone is not a sandbox.

Require actual Windows tests for outside-root read/write, original-source overwrite/truncate/delete, junction/reparse escape, inherited handles, child/grandchild cleanup, broker-mediated launch attempts, setup failure and owner-host crash. Any unsupported runtime, missing containment, incompatible host job or inconclusive proof returns unavailable; never degrade to an unsandboxed host launch. Direct provider/network and secret-enabled profiles need separate proof before exposure.

Verification for this note: primary-source browsing only; no native launch spike, production source edit or runtime acceptance claim.
